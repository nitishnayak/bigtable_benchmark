1. Purpose: what are we trying to prove?

The goal is to build repeatable evidence about Bigtable behavior under selected workloads—not to claim that one database is universally better than another.

Measure

Observe throughput, client-side latency percentiles, success/failure counts, and how results change with concurrency.

Validate

Confirm reads find expected rows and writes are present after the workload finishes.

Inform decisions

Combine benchmark data, server metrics, data model, operational needs, and comparable cost assumptions.

Workloads covered so far

  • Sequential point reads against known row keys.
  • Sequential point writes with a 512-byte payload.
  • Concurrent point reads with reusable per-worker clients.
  • Concurrent point writes with reusable per-worker clients.
  • A mixed workload of 50 reads and 50 writes submitted across 10 workers.
  • Read-scaling at 1, 5, 10, and 20 workers, with warm-up and three measured runs per level.
Current scope: these are small functional and concurrency experiments against one Bigtable instance/cluster configuration. They are a starting baseline, not a production capacity certification or a cross-database comparison.

3. Bigtable characteristics: strengths and trade-offs

Google Cloud Bigtable is a managed, wide-column NoSQL database designed for large-scale, low-latency workloads with high read/write throughput. It stores data in sorted rows, with column families and column qualifiers, and is often a good fit for time-series and key-based access patterns.

Strengths

  • Designed to scale to large datasets and high request rates.
  • Low-latency access for well-designed row-key lookups.
  • Managed service reduces the burden of operating database servers.
  • Suitable for time-series, telemetry, IoT, operational analytics, and large key-value workloads.
  • Supports row-level atomic mutations and strong consistency for supported access patterns.

Design considerations

  • Row-key design is critical; poor keys can create hotspots.
  • It is not a relational database: joins and ad-hoc relational queries are not its strength.
  • Schema and access patterns should be designed around known queries.
  • Capacity, replication, storage, backups, network, and monitoring choices affect cost.
  • Benchmark results depend on client placement, client reuse, request shape, payload, and cluster configuration.

Why row keys matter

Bigtable stores rows lexicographically by row key. A row key should support the primary access pattern while avoiding excessive concentration of traffic on a narrow key range. Sequential keys can be appropriate for some patterns, but monotonically increasing keys can create hotspots in some write designs. For production designs, evaluate key distribution, access patterns, and traffic over time.

Do not infer general superiority from this lab. To compare Bigtable with another database, run equivalent workloads with comparable data, consistency requirements, client placement, warm-up, concurrency, payload sizes, and cost assumptions.

4. Install, configure, and run

  1. Choose the correct Google Cloud project.
    gcloud config set project bigtable-benchmark-lab
gcloud config get-value project
  2. Authenticate in Cloud Shell.

    Cloud Shell normally supplies your signed-in Google identity. Verify the active identity and ensure it has permission to access the Bigtable instance and table.

    gcloud auth list
gcloud bigtable instances list
  3. Create or activate the Python virtual environment.
    python3 --version
python3 -m venv ~/bigtable-bench-venv
source ~/bigtable-bench-venv/bin/activate
python -m pip install --upgrade pip
gcloud config set project bigtable-benchmark-lab

    If the virtual environment already exists, do not recreate it; simply activate it.

  4. Install the Bigtable Python client library.
    python -m pip install google-cloud-bigtable==2.50.0
python -c "from google.cloud.bigtable_v2 import BigtableClient; print('Bigtable import OK')"
  5. Confirm table and data exist.

    Use the lab's inspection/verification scripts only after checking their code and required arguments. The benchmark read keys should exist in benchmark-table before the read test starts.

  6. Run a script from the home directory.
    cd ~
source ~/bigtable-bench-venv/bin/activate
python ~/benchmark_reads_scaling.py
Permissions: the identity used by the scripts needs appropriate Bigtable data access and permission to read the target instance/table. Follow your team's least-privilege IAM policy; avoid putting service-account keys in source control.

5. Python scripts and report files

This is the script inventory from the Cloud Shell directory. Descriptions marked “verify locally” are based on filenames and expected lab role; inspect the actual file before presenting exact implementation details to the team.

seed_bigtable.py

Expected to create/populate benchmark rows. Check its constants for row count, key pattern, column family, payload size, batch size, and error handling.

check_bigtable.py

Likely an environment/table inspection helper. Verify the exact checks and command-line behavior in the file before describing it as authoritative.

verify_bigtable.py

Likely validates that rows exist after seeding/writes. Confirm which key prefixes and counts it checks.

benchmark_reads.py

Earlier/general read benchmark variant. Inspect to determine whether it uses high-level or low-level API and whether it is sequential or concurrent.

benchmark_reads_direct.py

Measured sequential point reads using the low-level API, one request per row, consuming the returned stream.

benchmark_reads_concurrent.py

Concurrent point reads. The updated version reuses one Bigtable client per worker thread to avoid per-request client creation overhead.

benchmark_reads_scaling.py

Scaling test: 1, 5, 10, and 20 workers; 20 warm-up reads per level; 200 measured reads per run; 3 runs per level; reports throughput and latency percentiles.

benchmark_writes.py

Sequential point writes of 100 rows with a 512-byte payload; output records successful writes, elapsed time, throughput, and latency statistics.

benchmark_writes_concurrent.py

Concurrent point writes with 10 workers and reusable per-worker clients. Writes 100 rows with 512-byte payloads.

benchmark_mixed_workload.py

Runs a mix of 50 point reads and 50 writes using 10 workers. Useful as an initial mixed-workload functional benchmark, not a paced production traffic model.

seed_report.json

Seeding run metadata and performance summary; review it for actual inserted-row count and any errors.

read_benchmark_report.json

Sequential read results, including throughput and latency measurements.

write_benchmark_report.json

Sequential write results.

concurrent_read_benchmark_report.json

Concurrent read report. Check its scenario label because an earlier version created a client for each read and was slower than the client-reuse version.

concurrent_write_benchmark_report.json

Concurrent write report.

mixed_workload_report.json

Mixed read/write results, with read and write metrics reported separately.

bigtable_read_scaling_report.json

Scaling report with one record per worker count and run, plus success/error counts and latency percentiles.

README-cloudshell.txt

Existing notes; review for setup steps or environment-specific instructions.

grafana-public.yaml

Configuration file whose purpose depends on its contents. Inspect it before applying or publishing; ensure no credentials or sensitive endpoints are present.

7. What are we monitoring?

Python reports answer, “What did the client experience?” Cloud Monitoring helps answer, “What was happening on the Bigtable service while that workload ran?” Use both together.

Cluster CPU load / utilizationIndicates resource pressure and whether load increases as concurrency rises.Trend over the test window; sustained high load may indicate a need to investigate capacity, access pattern, or workload design.
Request count / request rateConfirms server-side request activity and helps correlate the test with service metrics.Changes during benchmark runs; ensure the selected metric and filters match the correct instance/cluster.
Server-side latencyHelps distinguish service latency from client/network overhead.Compare time ranges and metric definitions; do not assume the server metric is directly identical to Python's end-to-end latency.
Errors / retriesShows service/API failures or retry pressure.Any increase during concurrency or longer runs.
Storage bytesSupports capacity tracking and cost estimation.Stored data trend, with retention and replication assumptions accounted for.
Node count / cluster configurationProvides context for interpreting load and scaling behavior.Record node count and configuration for each benchmark run.

8. How to approach TCO / cost comparison

Throughput alone is not a TCO result. Cost should be calculated from a representative workload and a clearly documented configuration.

Capture these inputs

  • Region, cluster count, node count, node/storage configuration, and replication topology.
  • Stored data size and growth rate; data retention and deletion policy.
  • Read/write request volume, payload size, workload mix, peak/average traffic, and expected growth.
  • Backup/restore, networking/egress, monitoring, and operational requirements.
  • Availability, latency, consistency, and recovery objectives.
  • Current published pricing for the chosen region and configuration, checked at the time of the analysis.

For a fair comparison, run equivalent data and workloads on candidate services, measure throughput and latency under the same conditions, and compare the cost required to meet the same service-level objectives. Include engineering and operations effort if the proposal calls for total cost of ownership rather than infrastructure spend alone.

Do not extrapolate the observed 1-node test rate directly into a production bill or assume that multiplying nodes gives linear throughput. Validate with representative load, service limits, pricing, and service-specific scaling behavior.

9. Where Bigtable can be a good fit

Time-series / observability

Metrics, telemetry, and event histories when row-key design supports the read patterns and retention needs.

IoT and device data

Large volumes of device state, measurements, or timestamped readings indexed for known access patterns.

Personalization / user state

Low-latency lookups for large populations of users or entities when access is key-oriented.

Operational key-value access

High-volume reads/writes for large datasets where relational joins and complex ad-hoc SQL are not central requirements.

When another system may fit better

If the application depends heavily on relational joins, multi-row transactions, flexible ad-hoc queries, or a relational schema with rich constraints, evaluate a relational or analytical database as well. Choose based on access patterns and requirements, not on the benchmark headline alone.

  • Next Capture Cloud Monitoring metrics aligned to each run window.
  • Next Add repeated trials across more than one session/time window and document environmental conditions.
  • Next Run longer tests and increase operations gradually; watch error rates, latency, and resource pressure.
  • Next Test more representative row-key distributions, payload sizes, and read/write mixes.
  • Next Validate all rows and write failures, not only the summary throughput.
  • Next Perform a like-for-like alternative-database and TCO comparison if that is a proposal requirement.

Benchmark quality checklist

  • Record code version, project/region, instance/cluster config, client version, worker count, request count, payload size, and timestamps.
  • Separate warm-up from measured requests.
  • Reuse clients where appropriate; client construction per request can distort results.
  • Report p50/p95/p99 latency, throughput, failures, and correctness together.
  • Use the same dataset, key distribution, and client location when comparing configurations.
  • Keep test runs isolated from unrelated traffic where possible.

11. Troubleshooting

Import error for Bigtable

source ~/bigtable-bench-venv/bin/activate
python -c "from google.cloud.bigtable_v2 import BigtableClient; print('OK')"
If import fails, confirm the active Python and package installation: which python and python -m pip show google-cloud-bigtable.

Permission or authentication error

Check gcloud auth list, active project, and IAM access. Do not place credentials in a GitHub repository.

Rows are missing

Confirm the table and key prefix. The read benchmark expects seeded keys like bench#0000000000. Write tests use different prefixes such as writebench#, concurrentwrite#, and mixedwrite#.

Results vary significantly

Check whether the client was recreated for every request, whether other workloads were running, whether warm-up was included, whether the client region/network path changed, and whether the same number of requests was measured.

Cost or safety reminder

Benchmark workloads create requests and stored rows. Clean up test data only after confirming the target table/prefix and team retention requirements. Avoid running large tests against shared or production resources without approval.

13. Suggested KT walkthrough

  1. Start with the question: what evidence would help us evaluate Bigtable for the proposed workload?
  2. Explain the data model: table, column family, row-key patterns, payload, and why the row key matters.
  3. Walk through each workload: sequential reads/writes, concurrent reads/writes, mixed workload, and worker scaling.
  4. Show one script and one JSON report: identify scheduled operations, successful operations, elapsed time, throughput, latency percentiles, and errors.
  5. Show the scaling table: throughput increased from 4.67 reads/sec at one worker to 85.87 reads/sec at 20 workers, while observed p95 latency remained around 216–228 ms.
  6. Open Cloud Monitoring: align the time range with a benchmark and show CPU, request rate, latency, errors, and storage metrics that are available.
  7. State limitations honestly: this is an initial lab baseline; it is not maximum capacity, production readiness, or a proof that Bigtable beats another database.
  8. Close with next steps: correlate server metrics, run longer representative workloads, verify data correctness, and complete a like-for-like TCO study.
One-sentence takeaway: “We have built a repeatable starting benchmark that validates basic correctness and shows how client-observed Bigtable point-read throughput changes with concurrency; next we correlate it with service metrics and representative cost/performance requirements.”
